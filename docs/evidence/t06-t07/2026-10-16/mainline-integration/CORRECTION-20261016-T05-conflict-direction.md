## 二、真实演进链（以 `RuleAgentRunner.java` 为样本，blob 逐点核对）

   ├── 主线 58e1ef7 → ec1e362      blob 2f82467a   ← 主线演进

- T05 的 `6b79b0bf` 是在 `2f82467a` **之上**的新演进，不是旧版本。

## 三、更正后的结论

1. **T05 是更新的那一侧**，不是"停在旧版本"。
2. **T05 × T06 的 14 个冲突是"假冲突"（spurious conflict）**：
   `merge-base(T05, T06)` 被取到更早的 `5ee26d8`（`3c39d78b`），于是 git 看到
   "两边都改了同一区域"→ 报冲突。但 T05 侧实际上**已包含** T06 侧的内容
   （`2f82467a`）再加上自己的改动，两边并非对立的分支演进。
3. **`T05 × 主线` 之所以 0 冲突且结果正确**：此时 merge-base 是较新的 `58e1ef7`，
   主线侧该文件未变（= `2f82467a`），只有 T05 侧改了 → git 判定"单方改动"，
   直接取 T05 的 `6b79b0bf`。已实测合并树 `ac28aefb` 中该文件确为 `6b79b0bf`，
   **即正确应用了 T05 的更新演进，不丢主线内容**。
4. **因此这 14 个冲突不需要"语义裁决"**——它不是设计分歧。是否合 T05 是**范围决策**，
   不是技术障碍。

## 五、教训

不能只凭"两侧 blob 不同 + 有一侧与共同祖先相同"就判定谁陈旧。
必须确认**各分支的实际分叉点**（`merge-base`）与该文件在分叉点上的 blob，
否则会把"建立在新版之上的继续演进"误读成"停在旧版本"。
