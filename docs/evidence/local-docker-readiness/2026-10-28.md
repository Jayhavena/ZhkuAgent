## 现场与因果

用户现场：旧容器挂载曾指向已移开的 worktree；从当前目录重建后 SQL bind 已正确、卷为 `zhkuagent_zhkuagent_postgres_data`、healthy。但缺少非秘密 Compose 变量，宿主端口变为 `23031`。已有健康状态不能证明原应用 URL 或凭证可用。

根因分层：

1. `docker start` 复用容器创建时的绝对 bind 路径，无法随 worktree 移动更新。
2. 旧 Compose 端口变量空值会形成非预期宿主映射；缺库名/用户名还会使健康探针的语义不可靠。
3. 旧 ensure 只检查已启动引擎；旧 preflight 虽可选启动 Desktop，但用不可靠的应用名查找和无界原生命令，且两套逻辑重复。
4. Windows PowerShell 5.1 的 native 参数传递可能剥离 Go 模板内部双引号；改为 JSON 元数据和受控 Windows 参数编码。

## 实现保护

- 引擎模式与共享数据库模式分离；临时库测试只要求引擎，不启动原演示库。
- 固定本机 Linux context，校验本地命名管道，子进程清理远程 endpoint 覆盖，不改全局 context。
- 仅接受已知项目、服务、固定镜像、原数据卷；修复核对卷 driver/Compose labels。停止且漂移的容器未经认证不重建，避免把空卷初始化为替代库。
- 配置修复只用原卷，运行中的原库先只读认证。保持固定回环端口；同时检查 HostConfig 和实际发布端口。
- `restart: unless-stopped`、SQL 长格式只读 bind、禁止自动创建缺失 source 目录。源路径随当前脚本位置解析。
- 只读认证口令仅经继承环境传输；不回显容器 inspect 或 Compose 渲染配置；退出恢复环境。
- 命令、探针、等待均有限时；互斥锁防本入口并发重建。CLI 超时可能留下已被服务端接受的操作，不能按未发生处理。

### 真实本机恢复

实际执行：

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File knowledge/scripts/ensure-zhku-postgres.ps1 -RepairConfiguration -TimeoutSeconds 180
```

结果：

```text
[readiness] Repairing container configuration; keeping the verified existing data volume.
PostgreSQL ready: container=zhkuagent-postgres port=54329 volume=zhkuagent_zhkuagent_postgres_data authenticated=read-only
```

- 真实回环发布：`127.0.0.1:54329 -> 5432/tcp`。
- 真实卷标签：project=`zhkuagent`、volume=`zhkuagent_postgres_data`。
- 修复后容器 ID：`bcfa754ce8e6a3555ec3a76755b303ec81bfdef8d547887987a90516ac3b12f3`。
- 再通过普通 `cmd.exe /d /c` 执行 `ensure-zhku-postgres.cmd -CheckOnly` 和 `-RepairConfiguration` 均成功；后者未输出重建消息、ID 未变，确认幂等。
- 初轮容器内部回环认证存在 `trust` 绕过风险，不以该轮 `SELECT 1` 作为口令正确的证据。最终探针改为 `host.docker.internal` + 实际宿主发布端口；先用随机错误口令，要求非零退出且明确 `password authentication failed`，再用入口重新读取的原口令执行只读 `SELECT 1`。新实现真实 `-CheckOnly` 成功，证明错误口令确实被拒绝、原口令被接受；trust 或网络错误的拒绝分支新增三个回归用例。
- 旧 preflight 的 `-DockerOnly -CheckOnly` 和数据库 `-CheckOnly` 均成功。
- 人工演示 CMD 的 `-CheckEnvironment` 成功：实际 PowerShell 7.6.9，UTF-8 中文输出正确，databaseOperations=0、providerCalls=0。未运行演示、Maven 或业务测试。
