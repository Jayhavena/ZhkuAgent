## 三、结论：B 方案（精简载荷）没有空间

- 核验请求 **4457 字节，只占 65536 上限的 6.8%**；与决策侧请求（同批实测 4457 字节）同量级，**不是异常偏大**。
- 因此**"核验请求偏大导致超时"这一假设被排除**：瓶颈在**生成耗时**，不在载荷体积。
- 精简载荷最多只能省下几百字节（合同说明 1025、能力目录 623 已是语义必需），**不足以把 >10 秒的生成压到 10 秒内**。
  → **不建议走 B**（若强行精简，收益不可测且风险是削弱核验语义，属禁止方向）。

## 四、超时机制的复核（关键，影响可选方案）

真机第 4 次的截止时间是 `min(单次上限 10000ms, 整 run 剩余 ≈10.4s)`，实测 10020ms 撞满**单次上限**。这意味着：

- **只提高单次上限没有用**：整 run 45 秒里前 3 次决策 + 建库/检索已用掉约 34 秒，核验只拿到约 10.4 秒的剩余 run 预算。
  即使单次上限提到 20 秒，核验仍会被 `min(20s, 10.4s)=10.4s` 截住。
- **要放宽就必须同时放宽两处**：单次 10s→20s **且** 整 run 45s→90s（两者同属"提高预算"）。
- 另一种可能是核验响应生成较长（核验输出含需求清单、绑定与未决需求），或该次为偶发慢响应 —— **属假设，未验证**。
