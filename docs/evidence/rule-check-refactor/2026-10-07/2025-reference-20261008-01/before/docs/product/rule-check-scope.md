## 1. 项目定位与成功标准

**面向学生的校园规则查证助手，以 RAG 为主要技术路线，降低查阅、理解和判断成本。** 首期围绕校园教务规则，从一个有可靠资料的主题开始。

核心成功标准：

> 用户能够基于适用于当前情境的证据，正确理解规则、核对原文，并明确仍然未知的部分。

成功可以是确认规定、识别不适用、补齐必要条件，或明确当前依据不足。评价同时关注正确完成、原文可核对和所花时间。

收益假设：少翻文档、少误用规则、更容易核对与纠错。方向合理，收益仍需验证。目录整理、框架数量、回答率或测试数量增加不能替代上述收益。

## 2. 用户与产品责任

| 角色 | 主要任务 | 产品提供 |
| --- | --- | --- |
| 学生 | 查找现行规定，理解条件/例外，判断规则与自身情境的关系 | 自然语言查询、必要澄清、范围明确的解释、原文定位、未知项 |
| 资料维护者 | 核验来源、审核条款、发布/撤回、处理错误 | 原文对照、审查记录、版本/可见性管理、纠错修订与复验 |

首期回答公开且获准传播的规则，不接入真实个人成绩或教务办理系统。依据用户提供的条件解释规则时，明确条件是用户陈述；没有授权个人记录或审批依据时，不作官方资格确认。

经审核的部门/渠道用于指引，只有收到真实受理回执才可以说已受理；当前没有该办理能力。匿名反馈是问题信号，修订和复验由独立纠错流程记录。会话控制状态恢复与完整咨询历史分别设计。

## 3. 核心流程

**自然语言提问 → 必要澄清 → 检索已审核、学生可见的资料 → 解释条件与例外 → 提供原文依据。**

实际执行还包括证据资格检查、主张支撑校验和输出前复查。资料撤回、版本漂移或权限变化影响证据时，重新取证或停止下发结论。

第一版突出三个动作：看懂规则、核对原文、知道还缺什么或下一步去哪里核实。首页显示覆盖主题与资料版本/时效，不暗示整本手册、全部校园问题均已支持。

## 4. “充分证据”的判定

以下条件共同满足时，才能形成对应结论：

| 条件 | 应确认的内容 |
| --- | --- |
| 来源资格 | 来源已审核，允许学生查看，传播权利获确认 |
| 现行性 | 版本、生效区间、撤回/取代关系适用于本次查询；时效未知不能默认有效 |
| 适用范围 | 年级、培养类别、课程类别、学期等决定性条件匹配 |
| 条件完整性 | 必要条件、例外和关联条款完整，没有影响结论的未解决冲突 |
| 主张支撑 | 每项实质性结论均能对应原文跨度或审核后的结构化规则，数字/对象/否定词等一致 |

检索排名和模型自报分值只作辅助信号；合法引用编号只证明引用身份，不能单独证明事实正确。

## 5. 回答边界与目标状态

以下为**目标业务协议，尚未在业务代码实现**。状态与排队、运行、取消、失败等执行状态分开。

| 状态 | 使用条件 | 用户应看到 |
| --- | --- | --- |
| `ANSWERED` | 主要问题的证据与条件充分，结论有据 | 有适用范围的结论、条件/例外、原文与版本 |
| `PARTIALLY_ANSWERED` | 只能确认部分内容，但该部分独立成立，不依赖缺失证据 | 已确认内容及各自出处、明确未知项、当前不能作出的判断 |
| `NEED_CLARIFICATION` | 缺少会改变主要结论的用户条件，且现有规则可在补充后判断 | 必要追问、该条件为何影响结论；不先给肯定结论 |
| `INSUFFICIENT_EVIDENCE` | 缺少依据、范围未覆盖或时效无法确认，追问用户也不能补资料缺口 | 缺口与原因、可提供的合法原文、经审核的核实渠道 |
| `CONFLICTING_EVIDENCE` | 存在无法按范围/时间/取代关系消解的规则冲突 | 冲突点、各方原文与适用信息、待核实事项；不选定唯一结论 |

判定顺序：先核对证据资格；主要结论有未解决冲突则说明冲突，缺决定性用户条件则追问；证据充分才完整回答。其余情况下，仅在独立部分事实确实成立时部分回答，否则说明证据不足。

澄清、冲突或缺证回复可以包含独立确认的信息，但不能通过正文暗示整体问题已解决。状态须与实际结论一致。

### 部分回答的约束

以“截止日期能确认、申请资格不能确认”的边界示例说明：可以分别展示已确认日期的适用范围与原文，以及资格依据缺失；不能据此判断用户符合申请条件。此例仅说明产品行为，不代表实际学校规定。

缺失的例外可能推翻结论时，不生成整体肯定回答；在末尾加免责声明不能弥补这一缺口。只确认规则写明了某条件时，也不能自动确认用户已满足该条件。

每个已确认事实都有自己的证据；未确认内容单独列出。模型不得补全缺失数字、条件、资格或办理结果。

## 6. 澄清与结果体验

澄清只询问会改变结论的最少条件，优先采用易理解的选项。每次追问应能说明“这个条件不同，会影响哪项判断”；已有信息不重复问，资料缺失不通过不断追问用户来掩盖。

结果卡固定展示：

1. 当前状态与已确认结论。
2. 适用对象、条件与例外。
3. 原文段落/条款、来源名称、版本和有效时间；点击可定位并查看原件。
4. 未知项及尚不能形成的结论。
5. 必要补充信息或经审核的核实渠道。

来源更新时间、发布时间与生效时间分别表示，不用“更新较新”代替“规则仍有效”。界面不显示未经审核的草稿、内部材料或模型推理过程。

## 7. 第一版范围与技术路线

先完成一个主题的纵向流程，候选为现有公共选修规则；具体条款、来源和有效期在 R0 核验后冻结。来源尚未确认前，不称该主题已经可用。通过方向门禁后再扩大到三个有审核依据的主题。

保留现有 Java/Spring、PostgreSQL/pgvector 和执行机制，以 **RAG + 固定查证工作流** 为主线。模型用于理解提问、必要澄清辅助、证据选择与解释；程序掌握资料资格、版本、发布、授权、预算和输出约束。

首个切片的事实输出优先采用已审核模板或原文摘录，原文跨度与关键字段可核对。自由解释在支撑性评测通过后逐步开放；仍以RAG取证，不能降级到无证据的自由作答。

学分计算保留为技术示例，退出产品主任务。通用自主 Agent、近似索引、多机、完整历史、SSO和办理工单按路线图的P2触发条件单独评估。仓库名称暂时保留，不先全仓改名或迁目录。

## 8. 如何验证价值

使用真实学生问题，对照直接查官网/PDF，检查：

- 正确完成率：结论/澄清/拒答状态与适用条件正确。
- 查证时间：正确任务耗时，同时报告错误与超时。
- 原文核对：引用是否支持主张、能否定位实际段落和版本。
- 部分回答：已确认部分是否独立成立，未知项是否明确，有无暗示资格或完整结论。
- 澄清成本：追问次数、是否必要、补充后是否解决问题。

沿用路线图的单主题36题质量试验（20开发、16锁定报告）与5–8人方向对照；已知风险反例独立记录，不混入用户质量率。题组按难度匹配并平衡顺序，同任务简单改写按家族隔离；样本仅用于方向判断，不代表全校总体。

初始建议门禁：16题至少15题正确完成，关键反例零漏放，用户正确率不下降、正确任务时间中位数减少至少20%。这是待验证标准；实施前记录样本与口径，看到留出结果后不能降低标准。

详细口径见 [评估协议](rule-check-eval-contract.md)：先验证评分是否可信，再分别检查证据召回、答案支撑和执行结果；首轮人工评分，模型裁判独立校准后才考虑自动门禁。同题比较保留改善、退步和未知，报告差值与不确定性。上述计数与20%目标是有限样本决策线，不足以证明总体成功率、正确率非劣或版本显著提升；样本不足时明确“尚不能确认提升”。

若用户更快找到原文却仍误解条件，先改澄清和解释；若简单检索/模板已满足任务，保留简单路径；两轮针对性试验仍无改善，则暂停扩大资料和系统复杂度。
