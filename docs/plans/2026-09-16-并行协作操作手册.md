## 3. 分工建议

### 3.1 划分维度：**功能线 + Java 包边界**（不按 `agent/` 与 `knowledge/` 模块分）

理由：MVP 纵切的工作几乎全落在 `knowledge/` 模块；按模块分会导致一边包揽、一边闲置。按功能线纵向切分、用 Java 包边界做硬隔离，才能让两条线几乎不共享文件。

### 3.2 职责表

| | 线 A：检索 + 生成 + 评测 | 线 B：工具 + 编排 + 体验 |
| --- | --- | --- |
| 负责 Agent | **本 Agent（WorkBuddy）** | **另一个 Agent**（可互换，在同步板改一行即可） |
| 交付内容 | 向量检索、混合融合（RRF）、受控 RAG 生成、引用白名单校验、降级、版本化 Eval 与指标 | 校园工具集（学分计算/选课冲突等只读或纯计算工具）+ Function Calling、统一路由编排器、会话持久化、流式输出、答案卡升级 |
| 拥有的目录（可自由新建/修改） | `knowledge/.../rag/`、`.../routing/`、`.../eval/`（新包）+ `answer/` | `knowledge/.../tools/`（新包）+ `web/` 页面资源 |
| 需要协商才可动的共享文件 | `GroundedAnswer*`、`PublicElectiveConversationRouter`、`LocalPreviewConversationFacade`、`ZhkuLocalPreviewConfiguration`、三个 `pom.xml`、`migration/` | 同左 |
| Flyway 号段 | `V9`–`V11` | `V12`–`V14` |
| 分支 | `codex/campus-line-a` | `codex/campus-line-b` |
| worktree | `D:\alldesk\Projects\ZhkuAgent`（切到 line-a） | `D:\alldesk\Projects\ZhkuAgent-lineB`（新建） |

### 3.3 冻结契约（开分前先落、单独提交、之后只追加）

- 统一路由判定顺序：澄清 → 当期通知 → 高风险规则 → 检索增强 → 拒答/人工
- 引用白名单标识结构（生成层输出与服务端校验共用）
- HTTP 会话响应新增字段（只追加，不改旧字段语义）
- 新配置键/Profile 命名规范
- Flyway 号段（上表）

### 3.4 为什么这样切冲突最小

- 新功能各落在**新包**（`rag/` vs `tools/`），物理上不共享文件；
- 共享的少数"咽喉文件"全部列入**冻结/协商清单**，任何一方要动先在同步板登记；
- Flyway 号段、配置键、HTTP 字段三类"隐形撞车点"提前分配。

## 4. 分支与 worktree 创建命令（基线收口后执行）

```powershell
Set-Location D:\alldesk\Projects\ZhkuAgent

# 线 A 分支（当前 worktree 切换即可）
git switch -c codex/campus-line-a

# 线 B：新建 worktree + 分支
git worktree add -b codex/campus-line-b D:\alldesk\Projects\ZhkuAgent-lineB

# 验证
git worktree list
git branch --show-current
```

> 主线 `codex/zhkuagent-modules` 只接收合并，不在其上直接开发。
> 注意：worktree 的 `target/`、`node_modules/` 各自独立，线 B 首次构建需重新 `mvnw package`（前端如涉及还需 `npm install`）。

## 5. 协调机制

### 5.1 共享状态板（唯一事实源）

文件：`docs/plans/agent-sync/SYNC-STATUS.md`（已建好初始版）。

**更新时机（四个时刻必更新）：**
1. 开工：登记"当前任务"与"占用文件"；
2. 收工/提交：更新任务状态与最新 commit；
3. 合并前：填写"待合并"条目；
4. 合并后：更新基线 commit 与"最近合并"记录。

### 5.2 合并节奏：持续小步合并

- 每个**可独立编译 + 测试通过**的子任务完成即合并回主线（目标：每天 1–2 次，不超过 3 天不合）；
- 合并执行：在主线 worktree 上 `git switch codex/zhkuagent-modules && git merge codex/campus-line-X`；
- 合并后各自把自己的 line 分支 `git merge codex/zhkuagent-modules` 跟上主线。

### 5.3 合并前检查清单（逐条过，缺一不合）

```
□ 本分支 git status 干净，无遗留未跟踪文件
□ 只 add 了自己负责的路径；全程未用 git add -A / git add .
□ 未修改冻结契约文件；如已修改 → 已在 SYNC-STATUS"待协商"登记并获对方确认
□ Flyway：空库可从 V1 顺序跑到最新（号段无断层）
□ 全量测试通过：
  .\mvnw.cmd -f knowledge\pom.xml "-Dzhku.db.password=<密码>" "-DargLine=-Djava.io.tmpdir=<临时目录>" test
□ 若动过 agent/ 模块：另跑 agent 模块测试
□ 新能力同批提交证据账本（docs/evidence/）
□ TDD 纪律：红 → 最小实现 → 验证，本次有对应失败用例记录
□ SYNC-STATUS.md 已更新
```

### 5.4 冲突升级流程

```
发现需要改对方/共享文件
  → 停手，不改
  → 在 SYNC-STATUS"待协商事项"登记（事项/原因/建议）
  → 等对方确认后再动
  → 确认结果写回同步板
```

### 5.5 提交纪律（沿用项目既有约定）

- 禁止 `git add -A` / `git add .` / `git add -a`；只精确 add 本任务路径；
- 每次合并前 `git status --porcelain=v1` 人工核对；
- 不改写已执行的 Flyway 迁移；不 rebase 已合并进主线的提交；
- 不 push 任何远程（origin 修改后也一样，除非用户明确要求）。

## 6. 修改 origin 为自己的 GitHub 仓库

先在 GitHub 网页建好一个**空仓库**（不勾选 README/.gitignore/License，避免首次推送冲突），然后：

```powershell
Set-Location D:\alldesk\Projects\ZhkuAgent
git remote -v   # 现状：origin → liyupi/yu-ai-agent（上游教学仓库）

# 方案一（推荐）：直接替换 origin 地址
git remote set-url origin https://github.com/<你的用户名>/<你的仓库名>.git

# 方案二：保留上游作为 upstream 便于日后对照
git remote rename origin upstream
git remote add origin https://github.com/<你的用户名>/<你的仓库名>.git

git remote -v   # 验证
```

**要点：**
- `set-url` 只改本地配置，**不会上传任何代码**；只有显式 `git push` 才会推送；
- worktree 共享这份 remote 配置，改一次对所有 worktree 生效；
- 即使将来 `git push origin`，推送的也是你自己的提交历史，与上游教学仓库无关；
- 当前阶段不推送完全不影响双 Agent 协作 —— worktree 共享的是本地对象库，不依赖任何远程。
