# 开发问题记录（developer-issues）

> 这里记录开发过程中随手想到、暂时不需要立刻变成正式任务的问题。它不是 GitHub Issues 的替代品，也不是 ADR、设计文档或验收证据。

## 什么时候用

- 读代码、跑评测、讨论方案时冒出的疑问。
- 有一个初步判断，但还没验证，或者还没到做决策的程度。
- 需要先记下来，等后续会话继续查。
- 某个现象可能影响设计，但当前不值得单开 issue 或计划。

## 命名与状态

- 文件名：`YYYY-MM-DD-<英文短横线主题>.md`；同一天多个问题追加 `-02`、`-03`。
- 状态：
  - `OPEN`：还没开始查。
  - `INVESTIGATING`：已有初步理解，结论待验证。
  - `RESOLVED`：已有可复核结论。
  - `PROMOTED`：已升级为 GitHub Issue、ADR 或计划，条目里保留链接。
- 升级后不要删除原条目；把状态改为 `PROMOTED`，保留原始问题和当时理解，方便回看。

## 条目模板

```markdown
# <问题标题>

- 日期：YYYY-MM-DD
- 状态：OPEN / INVESTIGATING / RESOLVED / PROMOTED
- 来源：<会话、issue、代码阅读等>
- 相关主题：<检索 / 评测 / 前端 / ...>

## 原始问题

> <逐字记录当时的疑问>

## 背景

<为什么会产生这个问题；当时在做什么；相关约束>

## 当前理解

<代码事实、评测数字、推测分开写；推测明确标注>

## 待验证

- [ ] ...

## 相关文件

- [路径](相对链接)

## 变更记录

| 日期 | 变更 |
| --- | --- |
| YYYY-MM-DD | 首次创建 |
```

## 边界

- 不放密钥、数据库导出、整本 PDF、构建产物或用户隐私数据。
- 正式任务、设计决策和验收证据仍分别放 GitHub Issues、`docs/decisions/`、`docs/plans/`、`docs/evidence/`。
- 条目里的结论要标清楚是“已核对”“评测数字”还是“推测”，不要把模块级诊断写成生产结论。
