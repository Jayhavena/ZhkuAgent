## 一、问题背景：从“状态没重置”到“生命周期所有权错误”

### 1.1 最初看到的现象

原始 Agent 设计把以下内容放在可能长期存在的实例上：

- `state`：本次运行到了什么状态；
- `currentStep`：本次运行执行了多少步；
- `messageList`：本次运行的对话历史；
- `toolCallChatResponse`：某一步 think 产生、等待 act 消费的响应；
- 流式任务被提交到公共异步线程池，但没有保存可取消的任务句柄；
- SSE timeout、error、completion 和 worker finally 都可能触发结束逻辑；
- Lombok `@Data` 又给 Agent 配置生成了公共 setter；
- `YuManus` 同时被声明为 Spring 组件，又在控制器里每次手动 `new`。

直觉修复可能是：运行结束时把 `state` 重置为 `IDLE`。这个做法只能解除第二次调用
的状态门禁，却没有处理旧消息、步骤、当前 decision、后台线程和资源所有权。

### 1.2 三类可真实触发的业务场景

#### 场景 A：同一 Agent 实例顺序复用

```text
用户 A 运行结束
    ↓
Agent.state 保留终态，messageList 保留 A 的消息
    ↓
用户 B 复用同一实例
    ↓
要么因状态不合法无法启动，要么读取到 A 的历史
```

只重置状态会让第二次运行“能启动”，但不会让第二次运行“是干净的”。

#### 场景 B：同一实例并发执行

```text
运行 A：think 得到 decision-A ───────────────┐
                                               │ 实例字段被覆盖
运行 B：think 得到 decision-B → 写入共享字段 ─┤
                                               ↓
运行 A：act 读取到 decision-B
```

即使 `List` 换成线程安全集合，也只能避免集合结构损坏，不能保证 A 的消息和 decision
不会被 B 消费。这里缺的不是“线程安全容器”，而是“运行身份隔离”。

#### 场景 C：SSE 超时后立即开始新运行

```text
SSE timeout 回调到达
    ↓
如果回调直接把 Agent 重置为空闲并 cleanup
    ↓
旧后台任务可能仍阻塞在模型或工具调用
    ↓
新运行开始
    ↓
旧、新线程同时操作共享 Agent 或共享资源
```

`Future.cancel(true)` 也只表示发送中断请求。被调用的 SDK 是否响应中断，是另一个
事实。因此不能在“请求停止”的瞬间宣布“后台任务已经终止”。

### 1.3 根因的三层结构

第一层是数据归属错误：请求级数据放进了 Agent 实例。

第二层是控制语义混淆：请求停止、业务终态、资源清理、线程退出被当成同一件事。

第三层是资源所有权不清：公共线程池、Spring 单例和控制器手动创建共同造成“谁创建、
谁取消、谁清理、谁关闭”没有唯一答案。

所以完整根因可以概括为：

> 一个可复用对象同时扮演了 Agent 定义、单次运行上下文和异步资源管理者，导致
> 请求级状态、步骤级中间值、后台任务与容器级执行资源拥有不同寿命，却被放进同一
> 生命周期中管理。

### 1.4 为什么锁不是首选答案

给整个 `run()` 加锁可以把并发变成排队，但仍有三个问题：

1. 顺序复用时旧消息仍要靠人工清空；
2. 一个长模型调用会阻塞同实例上的所有后续请求；
3. SSE 回调与后台任务的停止、清理、终止语义依旧不清楚。

锁适合保护确实需要共享的资源；本来就应该属于单次请求的数据，优先做生命周期隔离。

#### 1.5.2 障碍一：先建了 RunContext，不等于问题已经修复

`AgentRunContext` 第一阶段测试全部通过时，它还没有被 `BaseAgent` 主链路使用。这个
阶段只能证明新领域对象自身的契约，不能证明旧共享字段已经消失。

这体现了一个重要审计原则：

```text
组件测试通过
≠ 调用链已经接入
≠ 原始缺陷已经闭环
```

因此后续专门编写“同一 Agent 连续运行两次”的 RED。旧实现第二次运行失败，才把
基础设施和真实缺陷连接起来。

#### 1.5.3 障碍二：不能只迁移三个明显字段

`state`、`currentStep`、`messageList` 是明显运行态；`toolCallChatResponse` 看起来像
普通缓存，实际是一次 step 的中间结果。并发下，运行 A 的 think 和 act 之间可能插入
运行 B 的 think，从而覆盖响应。

最终没有把它塞进一个更大的 context 字段，而是让 `think(context)` 返回不可变
decision，并直接传给 `act(context, decision)`。这是更细的生命周期判断：

- 消息和步骤属于一次 run；
- decision 只属于一次 step；
- 生命周期越短，越适合局部变量而不是共享对象字段。

测试还临时把 decision 改回共享字段，确认配对测试会失败，再恢复正确实现。这种
mutation 用来证明测试敏感性，不是为了制造虚假的项目 Bug。

#### 1.5.4 障碍三：异常不能被转换成普通步骤文本

如果 `ReActAgent.step()` 捕获所有异常并返回“执行失败”，外层循环可能继续运行，
最终甚至把 context 标为成功。修正后的规则是：

```text
think/act 抛出异常
    ↓
传播到 BaseAgent 运行边界
    ↓
标记 FAILED
    ↓
finally 中 cleanupOnce
    ↓
signalTermination
```

同步调用保留原异常因果链；流式调用向 emitter 完成错误信号。

#### 1.5.5 障碍四：并发测试曾出现环境冷启动噪声

调试中出现过首次 `UUID.randomUUID()` 初始化落入严格计时窗口，造成偶发超时。处理
过程没有直接增加 timeout，而是按以下链路排查：

```text
现象：首次并发用例偶发超时
→ 假设：业务死锁、同步条件缺失或 JVM 冷启动
→ 验证：比较首次与后续运行，观察线程实际到达位置
→ 根因：首次 UUID 安全随机初始化进入被测窗口
→ 修正：在正式同步计时前预热非业务冷启动
→ 回归：恢复原等待边界，多轮通过
```

这个案例说明 timeout 是报警器，不应先通过放宽报警阈值消除报警。

#### 1.5.6 障碍五：保存 Future 还不够，必须先绑定再提交

以下顺序仍然存在竞态：

```text
executor.execute(task)
→ task 已经开始
→ 才把 Future 写入 context
```

如果 SSE timeout 恰好落在中间，停止请求找不到句柄。最终顺序是：

```text
创建 FutureTask
→ 绑定到当前 RunContext
→ 提交执行器
→ wrapper 标记 workerStarted
→ 执行业务
```

`workerStarted` 又解决了另一个问题：任务还在队列时直接 `cancel()`，可能让包装器永远
不执行，写在 finally 中的 cleanup 和 termination 也失去机会。因此：

- worker 未开始：只记录 STOP_REQUESTED，让包装器随后启动并收尾；
- worker 已开始：额外调用 `cancel(true)` 请求中断；
- 两种情况都不能仅凭 Future 状态宣布 termination。

#### 1.5.7 障碍六：功能正确之外还有提交质量问题

流式句柄提交后曾发现行尾空格、文件末尾换行和整文件格式化导致的噪声 diff。处理时
先建立本地恢复分支，再恢复父版本、重放最小差异、重新测试并 amend。这里的教训是：

- `git show --check` 能发现部分空白问题，但不是所有文本质量问题；
- 功能测试通过不代表提交可审查；
- diff 噪声会掩盖真正的并发语义修改；
- 改写历史前必须确认提交没有共享到远端，并保留恢复点。

#### 1.5.8 障碍七：执行器所有权不能靠默认值暗示

10A 只把 `Executor` 变成注入点，并暂时保留公共池兼容构造器。这是为了让一个 RED
只对应“是否服从注入入口”，而不是同时引入 Spring 装配、Bean 作用域和拒绝策略。

10B 才删除兼容入口，并明确：

```text
Spring 容器
├── 单例、专用、有界的 agentRunExecutor
└── 单例 YuManusFactory
      └── 每次 create() 返回新的 YuManus
```

这样 Agent 是请求级创建物，执行器是应用级资源，二者生命周期不再混淆。

#### 1.5.9 障碍八：拒绝测试首次就是 GREEN，不能伪造 RED

真实饱和测试第一次运行便通过，因为已有提交失败收尾逻辑能够处理
`RejectedExecutionException`。工程上应记录“特性验证通过”，而不是为了漂亮故事先
人为破坏代码并把它称为历史缺陷。

为了确认测试不是无效断言，后续临时颠倒 cleanup 和 termination 顺序。上下文本身
立即拒绝非法时序，测试失败；随后恢复 mutation。这证明的是测试敏感性。

#### 1.5.10 障碍九：工具观察超时不等于测试超时

一次 Spring 所有权 GREEN 运行超过了命令工具最初 30 秒的观察窗口，但同一 Maven
进程继续运行后正常得到 BUILD SUCCESS。分类结果是冷编译/启动时间超过观察窗口，
不是 JUnit 断言超时。因此没有修改生产代码，也没有扩大测试等待时间。

#### 1.5.11 障碍十：SSE error 与取消语义不相同

第一版 `finishAfterLoop()` 看到任何 STOP_REQUESTED 都进入 `CANCELLED`。行为测试
揭示 emitter error 也被吞成取消：期望 `FAILED`，实际 `CANCELLED`。

最终映射为：

| 事件 | 停止原因 | 最终状态 | 理由 |
| --- | --- | --- | --- |
| 用户主动停止 | `USER_REQUEST` | `CANCELLED` | 调用方不再需要结果 |
| SSE timeout | `SSE_TIMEOUT` | `CANCELLED` | 通道生命周期终止 |
| 客户端断连/completion | `CLIENT_DISCONNECTED` | `CANCELLED` | 消费方离开 |
| emitter error | `SEND_FAILURE` | `FAILED` | 传输链路故障 |
| `send()` 抛 IOException | `SEND_FAILURE` | `FAILED` | 结果发送失败 |

第一停止原因优先，后到回调不能覆盖先到原因。

#### 1.5.12 障碍十一：`@Data` 破坏封装不是代码风格问题

运行态迁走后，`@Data` 仍为名称、提示词、最大步数和 ChatClient 生成公共 setter。
外部线程可以在运行中改变配置，使同一次 run 的不同步骤看到不同定义。

封装 RED 通过反射观察到 5 个真实公共方法。移除 `@Data` 后仅向子类保留 protected
访问入口，外部公共 setter 数量变成 0。这还不是完全不可变配置，但显著缩小了误用面。

## 二、方案决策：最终架构为何如此设计

### 2.1 先定义不变量，再选择类和 API

最终实现必须同时满足：

1. 每次运行都有独立 context 和唯一 runId；
2. 消息、步骤和停止原因不能跨运行共享；
3. 每步 decision 只能由同一步的 act 消费；
4. 任务句柄必须在提交前绑定；
5. 请求停止不能冒充真实终止；
6. worker 已开始后，停止请求会最佳努力地中断它；
7. cleanup 最多一次；
8. termination 必须晚于 worker 退出和 cleanup；
9. 提交被拒绝时也必须得到 FAILED 和完整收尾；
10. SSE timeout/error/completion 不能直接清理另一个线程正在使用的资源；
11. Agent 创建和执行器关闭必须有唯一所有者；
12. 外部不能通过公共 setter 绕过配置生命周期。

不变量是评审标准，类只是实现这些标准的工具。

### 2.2 最终对象关系

```text
应用级生命周期
┌──────────────────────────────────────────────┐
│ Spring                                       │
│  ├─ agentRunExecutor：单例、有界、负责关闭   │
│  └─ YuManusFactory：单例、负责组装依赖       │
└──────────────────────────────────────────────┘
                       │ create()
                       ▼
请求级生命周期
┌──────────────────────────────────────────────┐
│ YuManus：每个请求新实例，只保存 Agent 配置   │
│  └─ runStream()                              │
│       └─ AgentRunContext：每次运行新建        │
└──────────────────────────────────────────────┘
                       │ step(context)
                       ▼
步骤级生命周期
┌──────────────────────────────────────────────┐
│ ToolCallDecision：think 返回，act 立即消费   │
└──────────────────────────────────────────────┘
```

核心规则是：寿命不同的对象不要混在同一个所有权层级中。

### 2.3 `AgentRunContext` 承担什么

它收拢一次运行的：

- UUID `runId`；
- 用户输入和消息历史；
- 原子步骤计数；
- `state + stopReason` 一致快照；
- 后台 `Future` 句柄和 workerStarted 标志；
- cleanup 幂等门闩；
- 表示真实结束的 `CompletableFuture termination`。

它不保存 Agent 的系统提示词、模型客户端或工具定义，因为这些属于可复用定义。

### 2.4 为什么用一个不可变 Lifecycle 快照

如果状态和停止原因分别放在两个原子变量中，读线程可能观察到：

```text
state = STOP_REQUESTED
stopReason = NONE
```

把二者封装成不可变 record，再通过单个 `AtomicReference` 做 CAS，能一次发布一致业务
事实。它解决复合状态一致性，不等于让所有消息和业务步骤自动成为全局事务。

### 2.5 为什么不用 ThreadLocal 保存当前 context

流式执行涉及请求线程、执行器线程和 Servlet 回调线程。ThreadLocal 默认不跨线程，
若用 InheritableThreadLocal 或手工复制，又容易在线程池复用时残留。显式参数传递虽然
会改变方法签名，却能从代码上看见归属：

```text
step(context)
→ think(context)
→ act(context, decision)
```

显式依赖比隐藏的线程上下文更容易测试和审计。

### 2.6 为什么 termination 不能复用 Future.isDone()

`FutureTask.cancel(true)` 后，Future 很快可以显示 cancelled/done，但底层调用可能仍在
运行。`termination` 表示更强的业务事实：最终状态已确定，运行边界已经退出，cleanup
已经执行。二者回答的问题不同：

| 信号 | 回答的问题 |
| --- | --- |
| `taskHandle.cancel(true)` | 是否发出了中断请求 |
| `Future.isDone()` | Future 状态机是否结束 |
| `context.state()` | 业务最终结果是什么 |
| `context.termination()` | 业务边界是否退出并完成清理 |

### 2.7 为什么 cleanup 由 worker 所有

当 worker 已经在使用模型、工具或上下文资源时，SSE 回调线程直接 cleanup 会形成
use-after-cleanup。正确路径是：

```text
SSE 回调线程：requestStop(reason) + cancel(true)
                         ↓
工作线程：观察中断/停止 → 退出步骤 → 进入 finally
                         ↓
工作线程：finish → cleanupOnce → signalTermination
```

唯一例外是任务提交失败：worker 根本不会存在，因此提交线程必须承担失败收尾。

### 2.8 为什么用专用有界执行器

公共池的问题不是一定立刻出错，而是没有独立的容量和关闭边界。Agent 调用常包含
长时间网络等待，如果与应用其他并行任务共享池，会相互争用且无法单独调参。

初始配置为 core=2、max=4、queue=16，使用 `AbortPolicy`。这些数字只是可配置默认值，
不是压测结论。

拒绝策略取舍：

| 策略 | 是否采用 | 原因 |
| --- | --- | --- |
| `AbortPolicy` | 采用 | 容量满时明确抛出异常，可进入 FAILED 并收尾 |
| `CallerRunsPolicy` | 不采用 | 可能让 HTTP 请求线程执行长任务，`runStream()` 无法及时返回 |
| `DiscardPolicy` | 不采用 | 静默丢任务，context 可能永远没有 termination |
| `DiscardOldestPolicy` | 不采用 | 旧任务已返回 SSE，却可能在没有清理机会时被丢弃 |
| 无界队列 | 不采用 | 把过载隐藏成无限等待和内存增长 |

### 2.9 为什么 Agent 每请求创建、执行器单例共享

备选方案是把 YuManus 做成彻底无状态的单例。但当前尚未证明 ChatClient、工具回调和
ToolCallingManager 的所有协作方式都适合同一 Agent 实例并发复用，而且 protected
配置仍可被子类改变。

每请求 Agent 延续控制器原本的真实使用方式，风险较小；执行器则是昂贵、需要统一
容量和关闭的应用资源，适合单例共享。代价是每个请求会重新组装 Agent 和 ChatClient，
其创建成本尚未测量。

### 2.10 为什么不用 Spring request scope

request scope 会引入作用域代理，而流式后台任务可能比 HTTP 请求作用域活得更久。
这反而需要解释代理对象在请求结束后的可用性和销毁顺序。当前工厂模式更直接：创建
动作明确，Agent 不作为 Bean，执行器仍由容器管理。

### 2.11 为什么使用优雅关闭而非强制 shutdownNow

当前策略允许已经接受的任务完成，并等待有限时间。这样运行中和排队中的 context
都有机会进入包装器并执行 cleanup。

代价是：等待秒数只是容器等待上限，不是业务强杀能力。如果模型 SDK 永不返回，
线程可能继续存在。强制 `shutdownNow()` 同样只能发中断，不能杀死忽略中断的 Java
代码。因此真正解决外部阻塞还需要 SDK 超时、网络超时和隔离策略。

### 2.12 为什么只把 setter 收紧为 protected，而没有一次做到完全不可变

完全不可变的 AgentConfig 值对象是更强的长期方向，但会同时改变构造器、测试夹具和
子类初始化方式。10E 的目标是删除外部公共修改能力，用最小改动闭合已识别风险。

当前代价是子类仍能错误地在运行期间调用 protected setter。这个边界已明确记录，
没有被描述成“Agent 已完全不可变”。

- 早期教程文档非常长，过程证据存在重复；今后应以一份决策文档、一份账本和一份
  最终复盘为主；
- `AgentRunContext.java` 和部分测试夹具较长，可以在不破坏语义时抽取测试 harness；
- 当前 BaseAgent 配置只是 protected 可变，不是构造后完全不可变；
- 每请求创建 ChatClient 的成本没有测量；
- 选择性单元回归没有替代全量集成测试；

- cleanup 门闩表示“已经开始清理”，没有单独表达“清理成功”；清理动作抛异常时仍需
  更明确的失败协议；
- 队列中的任务在 worker 启动前收到停止请求时，为了保证 wrapper 有机会 cleanup，
  会继续占用队列位置直到被取出；规模变大时可能形成取消积压。

### 7.4 可复用工程方法论

面对任何异步任务生命周期问题，可以按以下顺序审计：

```text
1. 列对象：应用、资源池、任务定义、单次运行、单步中间值
2. 标寿命：谁创建、活多久、谁销毁
3. 找共享：哪些可变值被不同请求或线程同时看见
4. 写不变量：哪些顺序绝不能颠倒
5. 画失败时序：正常、异常、取消、超时、拒绝、关闭
6. 写确定性 RED：用同步原语控制顺序，不用 sleep 猜测
7. 做最小迁移：先隔离状态，再绑定任务，再治理资源
8. 注入执行边界：让排队、拒绝和关闭可测试
9. 做 mutation：仅在缺陷已不存在但需要验证测试敏感性时使用
10. 建证据边界：每个数字说明口径和不能外推的范围
```

## 十、方案如何变坏：故障模式与规模化退化

| 故障模式 | 小规模表现 | 放大后的退化 | 当前是否解决 |
| --- | --- | --- | --- |
| 外部调用忽略中断 | termination 迟迟不完成 | 工作线程被长期占满，队列满并拒绝新任务 | 否，只能观测和等待 |
| 线程池过小 | 偶发排队 | 正常流量也频繁拒绝 | 配置可调，但未压测 |
| 线程池过大 | 看似减少排队 | 上下文切换、内存和外部 API 限流压力上升 | 未测量 |
| 取消的排队任务不立即移除 | 暂时占一个队列位置 | 大量断连请求造成无效队列占用 | 未解决 |
| 每请求创建对象成本高 | 几乎不可见 | 高请求率下增加分配和 GC | 未测量 |
| 共享协作者非线程安全 | 偶发错误 | 随并发增加出现竞态 | 尚未逐项证明 |
| cleanup 自身失败 | 单个资源未释放 | 残留资源累积，门闩阻止再次清理 | 未完整解决 |
| SSE 回调顺序与测试不同 | 状态原因差异 | 特定容器/代理组合出现漏停或误分类 | 需要集成测试 |
| 单队列无公平性 | 慢任务阻塞后续 | 单一用户占满容量，其他用户饥饿 | 未解决 |
| 多 JVM 部署 | 本机取消正常 | 请求落到另一节点时找不到 context | 未解决 |

这张表是面试中最重要的部分之一。成熟的回答不是“方案不会坏”，而是能够说明它在
什么负载和外部条件下退化，以及下一层治理应放在哪里。

## 十一、核心知识地图与类比

### 11.1 AgentRunContext：每趟航班的飞行记录

Agent 像飞机型号定义，RunContext 像某一趟航班的记录。航班号、乘客、当前航段、
取消原因和落地确认都不能写回“飞机型号”里。上一趟航班结束后丢弃其记录，下一趟
自然得到全新状态。

### 11.2 requestStop 与 termination：按下急停和机器真正静止

按下急停按钮是 requestStop；控制器收到信号并开始刹车是 `cancel(true)`；转轴停止、
现场清理完毕并亮起安全灯才是 termination。不能因为按钮已经按下就让维修人员进入。

### 11.3 CAS：只有第一个人能改动公告牌

每个线程先读取完整公告牌，再尝试把“我看到的旧版本”替换成新版本。如果公告牌已被
别人改过，本次替换失败，重新读取。这样第一个停止原因能够保留，后到回调不能覆盖。

### 11.4 有界执行器：有固定工位和候车区的维修站

工作线程是工位，队列是候车区。候车区满后必须明确拒绝，不能把车无限堆到马路上，
也不能让接待员放下本职工作亲自维修一辆耗时很长的车。

### 11.5 cleanupOnce：唯一领取清理令牌

多个结束入口都可以尝试领取清理令牌，但只有一个成功。拿到令牌只证明“有唯一执行
者”，不证明清理必然成功，也不证明领取时机正确。

### 11.6 CountDownLatch：测试中的闸门

测试不说“睡 100 毫秒，猜线程应该到了”，而是让 worker 到达指定位置后打开闸门，
测试线程收到信号再触发取消。这建立明确的 happens-before，机器快慢不会改变故事。

## 十二、面试追问与回答骨架

### 12.1 基础层

#### 问题 1：这个 Bug 的根因是什么？

回答骨架：不是单一状态未重置，而是请求级状态、步骤级 decision、后台任务和应用级
执行器被放在同一个 Agent 生命周期。结果是顺序复用残留、并发串话和取消后旧线程
继续运行。方案首先纠正所有权，再建立停止和终止协议。

#### 问题 2：为什么 cleanup 中把 state 设回 IDLE 不够？

回答骨架：旧消息和步骤还在；后台 Future 可能只是收到取消请求而未退出；回调线程
可能与 worker 同时访问资源；IDLE 只是一项状态值，不能证明资源已清理。

#### 问题 3：为什么不用 synchronized？

回答骨架：锁能串行化访问，但不会自动区分用户数据，也会让长任务阻塞后续请求。
应该隔离的数据先隔离，确实共享的资源再同步。

### 12.2 并发与生命周期层

#### 问题 4：为什么状态和停止原因放在一个 AtomicReference？

回答骨架：二者共同表达一次生命周期事实。分成两个原子变量会产生交叉快照；不可变
record + 单次 CAS 能一致发布。

#### 问题 5：Future.cancel(true) 做了什么？

回答骨架：如果任务正在运行，它向线程设置中断；如果代码不检查中断或底层调用不
响应，任务仍可继续。Future 的取消状态不能替代业务 termination。

#### 问题 6：为什么任务句柄必须提交前绑定？

回答骨架：先提交后绑定存在时间窗口，任务可能已经开始，而 timeout 回调看不到句柄。
创建、绑定、提交的顺序保证停止线程能找到正确运行的任务。

#### 问题 7：为什么 worker 开始前不直接 cancel Future？

回答骨架：FutureTask 可能因此永远不执行包装器，finally 中的 cleanup 和 termination
没有机会运行。当前策略让它随后被调度、看见 STOP_REQUESTED、跳过业务并收尾；代价
是取消任务会短暂继续占队列。

#### 问题 8：为什么 timeout 回调不能 cleanup？

回答骨架：回调线程不知道 worker 是否仍在使用资源。它只能发停止请求，由 worker
退出业务边界后清理。提交被拒绝时没有 worker，提交线程才负责收尾。

### 12.3 执行器与 Spring 层

#### 问题 9：为什么选择专用有界池？

回答骨架：隔离 Agent 长任务与公共池使用者，显式规定线程、队列、拒绝和关闭边界。
有界性不会消除过载，而是把过载变成可测试、可观测的拒绝。

#### 问题 10：为什么不用 CallerRunsPolicy？

回答骨架：它会把长 Agent 任务推回 HTTP 请求线程，可能让 `runStream()` 无法及时
返回 emitter，并把执行压力传播到 Web 线程池。

#### 问题 11：为什么 YuManus 不继续做单例？

回答骨架：理论上完全无状态可做单例，但当前未证明所有共享协作者线程安全，配置也
未完全不可变。每请求实例是更小风险；执行器则由 Spring 单例管理。

#### 问题 12：awaitTerminationSeconds 能保证 30 秒后线程消失吗？

回答骨架：不能。它限制等待时间，不是 Java 线程强杀。外部调用忽略中断时仍需 SDK
和网络超时、隔离或进程级处置。

### 12.4 测试与证据层

#### 问题 13：你如何稳定复现并发问题？

回答骨架：使用 latch/barrier 控制两个任务到达关键点，使用手动执行器控制任务开始，
使用 core=1、queue=1 的真实池确定性制造饱和，不使用固定 sleep 猜线程调度。

#### 问题 14：拒绝测试一开始就通过，为什么还算有价值？

回答骨架：它是特性验证，不冒充 Bug RED。通过临时颠倒 termination 顺序验证断言
敏感性，恢复后回归；这证明测试能防退化。

#### 问题 15：25 个测试是否说明支持 25 并发？

回答骨架：完全不是。测试数、并发任务数、重复轮次和吞吐量是四种口径。当前最大
确定性业务并发隔离场景是双任务，另有小池饱和和顺序取消样本。

#### 问题 16：为什么不能说性能提升？

回答骨架：没有同环境修复前后基准，也没有真实 I/O 和负载。p95 只是内存取消协议
的本机样本，用来做回归，不是接口响应指标。

### 12.5 失效与扩展层

#### 问题 17：方案最可能在哪里失效？

回答骨架：模型或工具忽略中断导致 worker 长期占用；取消的排队任务暂时占容量；
cleanup 失败没有独立状态；多 JVM 找不到本机 context；真实网络回调顺序未验证。

#### 问题 18：规模放大后首先观察什么？

回答骨架：运行时间分布、活跃线程、队列深度、拒绝率、停止到 termination 的 p95/p99、
外部超时、CPU、堆和 GC。先测量再调整 core/max/queue，不能靠单元测试数字调参。

#### 问题 19：下一步如何改进取消的排队任务？

回答骨架：需要在不破坏“必须收尾”的前提下建立明确的启动/取消所有权 CAS，由提交
线程安全完成未启动任务的 cleanup，并从底层队列移除任务；不能简单 cancel 后遗忘。

#### 问题 20：如果要做分布式取消怎么办？

回答骨架：RunContext 需要外部持久化或注册表，runId 要能路由到执行节点，取消命令
需要幂等投递和状态确认，termination 需要跨节点可观察；当前内存对象无法解决。

## 十三、循序渐进学习路径

### 第一轮：建立目录认知

只回答四件事：

1. Agent、RunContext、Decision、Executor 分别活多久；
2. 共享字段为什么会串话；
3. requestStop 和 termination 有什么区别；
4. 最终正确顺序是什么。

正确顺序：

```text
请求停止
→ 对已运行任务发出中断请求
→ worker 退出业务步骤
→ 设置最终状态
→ 幂等 cleanup
→ 完成 termination
```

### 第二轮：沿代码阅读

建议顺序：

1. `AgentRunState` 和 `AgentStopReason`；
2. `AgentRunContext.start/requestStop/finish/cleanupOnce/signalTermination`；
3. `AgentRunTask.create` 的创建—绑定—启动协议；
4. `BaseAgent.run/runStream/finalizeRun`；
5. `ReActAgent.step` 的局部 decision；
6. `AgentExecutorConfig` 和 `YuManusFactory`；
7. `AiController` 的创建入口。

每读一个方法，只问：它由哪个线程调用、修改谁的状态、调用前后必须满足什么。

### 第三轮：沿测试理解真实缺陷

建议顺序：

1. 顺序复用和双任务隔离；
2. decision 配对；
3. think/act 异常；
4. 流式 worker 中断；
5. 执行器选择和饱和拒绝；
6. termination 与优雅关闭；
7. SSE 五场景；
8. 公共 API 封装。

对每个测试写一句：如果删掉哪条生产约束，它会在哪个断言失败。

### 第四轮：独立讲解

不看文档画出三张图：对象寿命图、停止时序图、线程池饱和图。然后用 3 分钟完成：

```text
现象 → 根因 → 核心不变量 → 方案 → RED/GREEN → 代价 → 失效边界
```

如果不能解释“为什么不是锁、ThreadLocal 或 state=IDLE”，就回到方案决策章节。

### 第五轮：批判性改进

任选一个未解决问题，例如 cleanup 失败或未启动任务取消，先写不变量和失败时序，
不要立即写代码。能提出比当前方案更强、同时承认代价的设计，才算真正掌握。
