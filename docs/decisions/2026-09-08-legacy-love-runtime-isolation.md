# 旧恋爱领域的默认运行时隔离

## 1. 问题与触发场景

项目的默认入口同时暴露了恋爱聊天和超级智能体。恋爱领域不只是一张前端卡片：

- `AiController` 提供四个 `/ai/love_app/**` HTTP/SSE 路由；
- `LoveApp` 是 Spring `@Component`，会构造聊天客户端、对话记忆和工具依赖；
- 文档加载器、本地向量库和云端 RAG 顾问会在默认上下文中注册；
- 前端路由、首页、SEO 元数据和 README 继续宣传该领域。

只删除首页卡片时，用户仍可直接调用后端接口，应用也仍可能加载恋爱语料并创建相关 Bean。
这会造成“界面上消失、运行时仍存在”的错误边界。

## 2. 决策

采用两阶段迁移：当前阶段默认隔离，研究 Agent 主链路稳定后再物理删除。

默认隔离的定义是：

1. 删除公开的恋爱 HTTP/SSE 路由；
2. 使用 `features.legacy-love.enabled=true` 作为唯一显式开启条件；属性缺失或为 `false`
   时，不注册 `LoveApp`、恋爱文档加载器、内存向量库和云端 RAG 顾问；
3. 移除默认前端路由、首页入口和公开文案；
4. 保留旧源文件、语料、历史测试和历史 Git 证据，但它们不属于默认发布链路。

该条件开关采用 Spring Boot `@ConditionalOnProperty`。`havingValue = "true"` 且未设置
`matchIfMissing`，因此缺失属性默认不匹配，避免“忘记配置却意外开启”。

## 3. 为什么不直接删除

直接物理删除看似彻底，但研究 Agent 的 RAG 与任务入口尚未落地。当前就删除会把三个问题
混在一次改动中：领域替换、旧代码清理和新能力交付。发生启动或构建回归时，无法区分究竟是
替换链路未完成，还是删除误伤了可复用设施。

替代方案及结论：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 仅移除前端页面 | 不采用 | 后端路由和启动期 RAG Bean 仍然存在。 |
| 现在物理删除所有 Love 文件 | 暂不采用 | 新研究主链路尚未替代，回退和排错成本高。 |
| 默认关闭、显式开启 legacy | 采用 | 对外边界立即收敛，同时保留可核验的迁移与回退路径。 |

## 4. 收益与代价

收益：默认应用不再发现恋爱 HTTP 入口，也不创建对应的聊天、语料加载与 RAG Bean；公开网页
和 README 不再把恋爱功能作为当前能力宣传。

代价：旧功能不再默认可用。若要临时恢复，必须同时开启 `features.legacy-love.enabled=true`、
恢复旧前端路由，并确认旧接口、模型密钥和依赖仍可工作。开关只解决 Spring Bean 注册，
不能自动修复旧第三方 API、旧提示词或旧测试中的外部依赖。

## 5. 如何失效与能力边界

- 有人重新加入 `/love_app/**` 映射时，默认 Bean 关闭不会阻止一个新的控制器返回其他结果；
  因此需要 MVC 路由回归测试。
- 有人新建未加条件的 Love Bean 时，现有四个 Bean 的测试不会自动覆盖它；后续物理删除阶段
  仍需进行目录和依赖审计。
- 已构建的旧前端静态文件、浏览器缓存或外部反向代理缓存不会因源码变更自动消失，需要部署
  流程更新产物并清理缓存。
- 该方案不实现研究任务、持久化、恢复、GitHub 调研或新的 RAG 知识库；它只收紧旧领域边界。
- 该方案不证明性能、吞吐量、生产故障率或多实例安全。

## 6. 验证标准与证据

验证分层进行：

1. `LegacyLoveEndpointIsolationTest`：四个旧 HTTP/SSE 路径在 Spring MVC 中均返回 404；
2. `LegacyLoveRuntimeIsolationTest`：默认上下文没有 `LoveApp` Bean；
3. `LegacyLoveRagRuntimeIsolationTest`：默认上下文没有恋爱文档加载器、向量库和云端顾问；
4. Vite production build：默认路由构建成功，移除路由后不存在断裂导入；
5. 现有 Agent 生命周期聚焦回归：确认这次控制器和条件化配置未破坏既有 Agent 生命周期能力；
6. `git diff --check`：确认提交前没有空白错误。

原始命令输出保存在 `target/evidence/legacy-love-isolation/`，不纳入 Git。结构化结论与
测试计数在实现完成后写入证据账本；不能以这些功能测试宣称性能提升或生产收益。
