## 1. 背景与可观察问题

`BaseAgent` 已经把一次运行的状态迁移到 `AgentRunContext`，并通过 `AgentRunTask` 在提交前绑定可取消任务句柄。当前仍有两个生命周期问题没有解决：

1. `BaseAgent.runStream()` 直接向 `ForkJoinPool.commonPool()` 提交长时间运行的 Agent 任务，调用者无法注入、隔离、配置或管理这个执行资源。
2. `YuManus` 同时带有 Spring `@Component` 单例身份，而 `AiController` 又在每次请求中手动创建新实例，形成两套互相矛盾的 Agent 所有权模型。

这不是单纯的代码风格问题。执行器决定后台任务何时开始、能否被接受、应用关闭时由谁回收；Agent 实例的作用域则决定可变配置和协作者是否可能被多个请求共享。

## 2. 触发场景与最小时序

### 2.1 公共线程池争用

当应用内其他并行任务也使用公共池，或者多个 Agent 流式任务长时间等待模型和工具返回时，会出现以下时序：

```text
其他公共池任务占满工作线程
        ↓
Agent 流式任务进入公共队列或迟迟不能启动
        ↓
SSE 已经返回，但后台任务启动时间不可控
        ↓
停止、超时和应用关闭难以形成清晰的资源归属
```

当前没有压力测试，因此不能断言这一问题已经在某个并发量下发生；能够确认的是，代码没有提供专用容量边界和注入入口。

### 2.2 Agent 所有权冲突

`@Component` 默认表达由 Spring 容器管理的单例对象，而控制器手动 `new YuManus(...)` 表达每次请求独占的新对象。两种方式同时存在会造成：

- 阅读代码的人无法从类型声明判断真实作用域；
- 未来若有人改为注入 `YuManus`，可能无意中共享 Agent 实例；
- Agent 构造依赖和执行器依赖分散在控制器中，生命周期边界无法集中审查。

### 2.3 有界执行器饱和

引入专用有界执行器后，问题不会消失，而会从“队列或公共资源无边界争用”转化为“容量满时明确拒绝”：

```text
工作线程全部占用 + 等待队列已满
        ↓
新任务被拒绝
        ↓
本次 RunContext 必须进入 FAILED
        ↓
cleanup 只执行一次
        ↓
清理完成后才能标记 terminated，并向 SSE 报告错误
```

拒绝是有界系统的正常故障模式，必须有测试覆盖，不能依赖默认异常传播。

## 3. 根因与生命周期不变量

### 3.1 根因

- 执行策略硬编码在领域基类中，导致任务语义和资源管理耦合。
- Agent 创建职责散落在控制器，Spring 注解表达的作用域与实际创建方式冲突。
- 当前测试能够验证中断链路，却难以替换执行环境来稳定复现排队、拒绝和关闭行为。

### 3.2 必须保持的不变量

后续修改必须继续满足以下约束：

1. 每次运行拥有独立的 `AgentRunContext` 和唯一 `runId`。
2. 任务句柄必须在提交前绑定，避免“停止请求早于句柄发布”的竞态。
3. 停止请求只负责发出取消信号；后台工作线程负责最终 cleanup 和 termination。
4. `Future.cancel(true)` 只代表已请求中断，不代表业务线程已经退出。
5. cleanup 必须幂等，termination 必须发生在后台任务退出且清理完成之后。
6. 提交失败或执行器拒绝时，本次运行必须进入 `FAILED`，不能遗留为运行中状态。
7. 不能使用 `CallerRunsPolicy` 让控制器请求线程执行长时间 Agent 任务，否则 `runStream()` 可能不能及时返回 SSE。
8. 执行器满载时必须保持资源有界，不能退化为无界队列。

## 4. 候选方案与取舍

### 方案 A：每请求一个 Agent + Spring 单例专用执行器（采用）

Agent 保存配置和协作者引用，但一次请求只创建一个 Agent；所有 Agent 共享由 Spring 管理的专用执行器。`BaseAgent` 只依赖 JDK `Executor`，不依赖 Spring 的具体实现。

选择理由：

- 延续控制器当前真实使用方式，不要求一次完成 Agent 全面无状态化；
- 避免在没有证据时假设 `ToolCallingManager` 等协作者适合由同一 Agent 实例并发共享；
- 专用执行器可以配置线程数、队列容量、拒绝策略和关闭行为；
- 通过构造器注入，可以用受控执行器稳定验证任务提交、排队和拒绝时序；
- Agent 所有权与执行资源所有权分离：工厂创建 Agent，Spring 容器管理执行器。

代价：

- 每个请求都会构造 Agent、`ChatClient` 和工具调用管理对象，存在尚未测量的创建成本；
- 需要把执行器依赖沿 `BaseAgent → ReActAgent → ToolCallAgent → YuManus` 构造链传递；
- 有界队列会让过载从隐性等待变为显式拒绝，调用方必须正确处理。

### 方案 B：把 `YuManus` 保持为单例并完全无状态化（暂不采用）

理论上可以让所有运行数据都只存在 `AgentRunContext`，单例 Agent 只保留不可变、线程安全的协作者。

暂不采用的原因：

- 当前尚未证明所有模型、工具和工具调用管理协作者都支持同实例并发；
- `BaseAgent` 仍使用 Lombok `@Data` 暴露可变配置 setter，单例化需要更大范围封装；
- 一次同时完成无状态化和执行器改造会扩大回归面，难以定位 RED 的真实原因。

这可以作为后续独立重构，而不是当前修复的前置条件。

### 方案 C：使用 Spring request scope 管理 Agent（暂不采用）

请求作用域可以表达每请求实例，但会引入作用域代理和 Web 容器绑定。流式后台任务可能在 HTTP 请求作用域结束后继续运行，反而需要额外处理代理和销毁时序。对当前个人项目而言，复杂度高于收益。

### 方案 D：继续使用 `ForkJoinPool.commonPool()`（不采用）

它修改最少，但没有专用容量、拒绝策略和清晰关闭归属，也无法隔离 Agent 长任务对其他公共池使用者的影响，因此不能解决本阶段问题。

## 5. 最终设计与职责边界

### 5.1 对象关系

```text
Spring 容器
├── AgentRunExecutor（单例、专用、有界、容器负责关闭）
└── YuManusFactory（单例）
    ├── ChatModel（共享依赖）
    ├── ToolCallback[]（共享依赖）
    └── create()
        └── YuManus（每次请求新实例）
            └── BaseAgent.streamExecutor（仅依赖 Executor 接口）

AiController
└── 每次请求调用 YuManusFactory.create()
    └── agent.runStream(message)
```

### 5.2 计划修改的文件

| 文件 | 计划修改 | 技术目的 |
| --- | --- | --- |
| `BaseAgent.java` | 构造器接收并保存 `Executor`；`runStream()` 使用注入执行器 | 移除公共池硬编码，建立可测试的执行入口 |
| `ReActAgent.java` | 增加构造器并向父类传递执行器 | 保持继承链依赖完整 |
| `ToolCallAgent.java` | 构造器接收执行器并向父类传递 | 保持工具 Agent 创建方式明确 |
| `YuManus.java` | 移除 `@Component`；构造器接收执行器 | 消除单例与手动创建的冲突 |
| `YuManusFactory.java` | 新增 Spring 工厂，每次创建新 `YuManus` | 集中表达 Agent 所有权和依赖组装 |
| `AgentExecutorConfig.java` | 新增专用有界执行器 Bean | 建立容量、拒绝和关闭边界 |
| `AiController.java` | 改为注入工厂并按请求创建 Agent | 控制器不再自行组装底层依赖 |
| 现有 Agent 测试 | 为测试 Agent 显式传入受控执行器 | 保持测试隔离并适配构造链 |
| 新增执行器测试 | 验证注入入口、真实饱和拒绝和失败生命周期 | 形成本阶段 RED → GREEN 证据 |
| 证据账本 | 记录命令、数量、结果、提交号和边界 | 保留可核验结论 |

实际文件范围以实施前再次扫描为准；若发现其他构造点，必须先更新设计范围再修改。

### 5.3 执行器初始策略

专用执行器采用有限工作线程、有限等待队列和显式拒绝策略。初始容量只是可运行默认值，不是性能调优结论；具体值将在实施预览中列明，并允许通过配置调整。

拒绝策略使用 `AbortPolicy` 或等价的快速失败语义，不使用：

- `CallerRunsPolicy`：可能让 HTTP/SSE 请求线程执行长任务；
- `DiscardPolicy`：任务静默丢失，RunContext 可能永远不能终止；
- `DiscardOldestPolicy`：被丢弃的旧任务可能已经向客户端返回 SSE，却没有机会完成清理。

### 5.4 提交失败时序

```text
创建 RunContext
  → 创建 FutureTask
  → 提交前绑定任务句柄
  → executor.execute(task)
       ├── 接受：工作线程启动并负责最终清理
       └── 拒绝：提交线程将状态置为 FAILED
                   → 幂等 cleanup
                   → 标记 terminated
                   → SSE completeWithError
```

只有成功提交后，工作线程才拥有最终清理职责；提交失败时没有工作线程，因此由提交线程完成相同的失败生命周期。

## 6. 分阶段实施范围

为了让测试失败原因保持单一，实施拆为三个可审阅阶段：

### 阶段 10A：执行器注入接缝（行为保持）

- 在 `BaseAgent` 建立受保护的 `Executor` 构造器依赖；
- 暂时保留无参构造器，并让它显式委托给原有公共池，避免本阶段改变
  `YuManus @Component` 的 Spring 装配行为；
- 用受控执行器验证 `runStream()` 确实服从注入入口；
- 保持已有 12 项生命周期测试回归通过。

这一阶段只建立替换接缝，不宣称已经完成资源隔离。无参构造器仍使用公共池，
这是明确的过渡状态，必须在 10B 中删除，不能成为长期兼容入口。

### 阶段 10B：Agent 所有权、专用有界执行器与拒绝场景

- 删除 `BaseAgent` 的公共池兼容构造器，把 `Executor` 依赖贯通整个 Agent
  继承链；
- 新增 `YuManusFactory`，移除 `YuManus @Component`，控制器改为每请求创建 Agent；
- 新增 Spring 管理的专用执行器；
- 设置有限线程和有限队列；
- 使用真实小容量线程池制造“运行中、排队中、被拒绝”场景；
- 验证拒绝运行进入 `FAILED`、cleanup 一次、termination 在清理后发生；
- 记录确定性的并发任务数量和重复轮次，但不把它称为压力测试或性能结果。

### 阶段 10C：关闭与资源有界性

- 明确应用关闭时对运行中和排队任务的策略；
- 验证停止请求到真实 termination 的延迟采集方法；
- 检查执行器关闭后是否仍有 Agent 工作线程和未终止 RunContext；
- 在同一环境下多轮重复后，才形成任务残留和终止延迟证据。

阶段 10C 可能需要运行上下文注册表或更明确的关闭协调器。没有完成该阶段前，不宣称“应用关闭时所有任务均可可靠终止”。

## 7. 预期收益与引入代价

### 7.1 成功实施后能够解决

- 消除 `YuManus` 的两套生命周期表达，明确为每请求实例；
- 将流式 Agent 任务从公共池迁移到可注入、可配置的专用资源边界；
- 容量满时快速、可观察地失败，避免静默丢任务；
- 能用确定性测试构造排队和拒绝场景；
- 为后续采集停止延迟、任务残留和资源有界性建立入口。

### 7.2 同时带来的代价

- 构造器签名和测试夹具增加；
- 需要维护线程池容量配置；
- 过载请求会收到显式失败，产品层可能需要友好错误或重试策略；
- 应用关闭可能需要等待长任务，或者在超时后接受未完成外部调用的现实；
- 每请求创建 Agent 的成本尚未测量。

## 8. 方案如何失效与规模化退化

| 故障模式 | 如何变坏 | 预防或后续验证 |
| --- | --- | --- |
| 模型或工具忽略线程中断 | `cancel(true)` 已调用，但工作线程继续占用 | 以 `RunContext.terminated` 而非 Future 状态判断真实结束；阶段 10C 测终止延迟 |
| 任务执行时间过长 | 有限线程长期被占用，队列积压并开始拒绝 | 记录排队和拒绝；后续为外部调用设置独立超时 |
| 线程池配置过小 | 正常流量也频繁拒绝 | 用真实负载基准调参，不能依据单元测试数量决定 |
| 线程池配置过大 | 线程切换、内存和外部 API 并发压力增加 | 同环境采集 CPU、内存、延迟和外部限流响应 |
| 单队列缺少公平性 | 慢任务或单一用户占满容量，其他请求饥饿 | 后续评估租户隔离、优先级或配额；当前方案不处理 |
| 应用关闭时仍有排队任务 | 若任务从未进入包装器，可能无法执行最终清理 | 阶段 10C 专门设计关闭协议和残留检查 |
| 工厂共享了非线程安全协作者 | 不同 Agent 仍可能经共享依赖发生竞态 | 对共享依赖逐项确认契约或改为每 Agent 创建；当前没有充分证据 |
| 多实例部署 | 取消信号和 RunContext 只存在本 JVM | 需要分布式任务标识、路由和持久化；不属于本阶段 |

## 9. 能力边界

本方案不解决：

- 外部大模型或工具调用自身不支持取消的问题；
- SSE 网络层的所有超时、断连、发送失败语义；这些需要独立端到端场景验证；
- 跨 JVM、跨节点的运行状态和取消协调；
- 业务级重试、幂等请求和结果持久化；
- 公平调度、租户配额、任务优先级；
- 性能提升、吞吐量提升或生产故障率下降；这些目前均尚未测量；
- 所有共享协作者的线程安全性；需要逐个依据契约或并发测试补证据。

## 10. RED → GREEN 验证设计

### 10.1 阶段 10A 的 RED

使用一个可人工推进的测试执行器承接真实 `Runnable`：调用 `runStream()` 后，在测试显式执行任务前，Agent 的步骤不应开始；执行任务后，运行应完成。当前硬编码公共池会绕过该执行器，使行为断言失败。

该测试验证真实控制流，不通过读取私有字段、扫描源代码或只断言 mock 调用完成。

### 10.2 阶段 10A 的 GREEN

`BaseAgent` 改为使用构造器注入的 `Executor` 后，任务只会在受控执行器推进时运行。随后回归现有 12 项测试，确认状态、消息、步骤、decision、异常、中断、cleanup 和 termination 约束没有退化。

### 10.3 阶段 10B 的 RED/GREEN

使用真实的小容量专用线程池稳定构造：

- 第 1 个任务占用唯一工作线程；
- 第 2 个任务进入唯一队列位置；
- 第 3 个任务触发拒绝。

GREEN 必须验证第 3 次运行进入 `FAILED`、cleanup 恰好一次、termination 已完成且 SSE 收到错误；释放阻塞后，前两个任务也必须正常退出，测试不能遗留线程。

这里的“3 个任务”只是确定性故障测试的任务数量，不代表系统支持的并发规模。

### 10.4 失败分类和记录

任何偶发失败都按以下顺序记录：

```text
现象 → 假设 → 验证 → 根因 → 修正 → 回归
```

不得先延长等待时间。优先检查是否缺少 happens-before 条件、锁存器是否在正确时点释放、线程池是否正确关闭，再判断是否为环境冷启动噪声。

## 11. 证据计划与结论强度

原始输出保存在 `target/evidence/`，不进入 Git；结构化结论进入 `docs/evidence/AgentRunContext-证据账本.md`。

每次记录至少包含：

- 日期、操作系统、JDK 和 Maven 版本；
- 分支、提交号或“尚未提交”、工作区范围；
- 完整测试命令；
- 测试类和测试数量；
- 成功、失败、错误、跳过、超时数量；
- 并发任务数与重复轮次（如适用）；
- 能证明和不能证明的结论；
- 原始输出相对路径。

预期可以形成的证据：

- 注入执行器实际控制 Agent 后台任务；
- 已有 12 项迁移测试在构造链调整后继续通过。

完成阶段 10B 后才可以追加：

- 每请求工厂返回不同 Agent 实例；
- 小容量真实线程池的拒绝生命周期正确；

仍不能形成的结论：

- 高并发能力；
- 吞吐量或响应时间提升；
- CPU、内存下降；
- 线上故障率下降；
- 所有 SSE 断连场景均安全；
- 所有外部模型和工具均能及时响应中断。

## 12. 简历表述边界

完成阶段 10A 和 10B，并取得真实证据后，可以保守表述为：

> 将流式 Agent 后台任务从公共线程池迁移到可注入的专用有界执行器，统一每请求 Agent 的生命周期归属，并以真实饱和场景验证任务拒绝后进入 FAILED、幂等清理及终止时序。

在没有进一步测量前，禁止写：

- “支持高并发 Agent 调度”；
- “吞吐量提升 X%”；
- “平均响应时间降低 X%”；
- “彻底解决线程泄漏”；
- “线上故障率降低 X%”。

## 13. 已确认的关键决策

2026-09-05 已确认以下决策：

1. 采用“每请求一个 Agent、单例共享专用执行器”的所有权模型；
2. 容量满时快速失败，不让请求线程代跑，也不静默丢弃；
3. 把关闭与残留验证单独放在阶段 10C，不在 10A/10B 提前宣称完成；
4. 前两个阶段只形成并发正确性证据，不形成性能结论。

## 14. 阶段 10A 实际结果

阶段 10A 已完成执行器注入接缝：`BaseAgent.runStream()` 不再直接硬编码调用
`ForkJoinPool.commonPool().execute(...)`，而是把已完成提交前绑定的
`FutureTask` 交给构造器注入的 `Executor`。

测试使用手动推进的真实执行器控制任务开始时点。修改前聚焦测试稳定得到
`expected: 1 but was: 0`；修改后同一测试通过。最终阶段回归共包含 6 个测试类、
13 项测试，结果为 13 成功、0 失败、0 错误、0 跳过。

详细命令、分类和原始输出位置见
`docs/evidence/AgentRunContext-证据账本.md` 的“记录 03”。

本阶段保留了委托给公共池的无参构造器，因此生产环境尚未获得专用线程池隔离，
也没有形成并发规模、吞吐量、响应延迟或资源有界性证据。这些仍属于 10B/10C。

## 15. 阶段 10B 实施预览

### 本阶段解决的问题

阶段 10A 只建立了注入接缝，生产构造链仍通过兼容无参构造器使用公共池；同时
`YuManus` 仍具有 Spring 单例组件身份，控制器却每次手动创建实例。本阶段要统一
这两条互相冲突的所有权路径，并为流式任务建立显式容量边界。

### 计划文件与关键差异

| 文件 | 动作 |
| --- | --- |
| `config/AgentExecutorConfig.java` | 新增 Spring 管理的专用有界执行器 |
| `agent/YuManusFactory.java` | 新增每请求 Agent 工厂 |
| `BaseAgent → ReActAgent → ToolCallAgent → YuManus` | 贯通 `Executor` 构造器，删除公共池兼容入口 |
| `AiController.java` | 改为调用工厂，不再手动组装模型和工具 |
| 现有 Agent 测试 | 显式提供同步或异步测试执行器 |
| 新增配置、作用域和拒绝测试 | 验证真实容器行为与真实线程池饱和行为 |

### 初始执行器边界

- 核心线程：2；
- 最大线程：4；
- 有界队列：16；
- 线程名前缀：`agent-run-`；
- 拒绝策略：`AbortPolicy`，容量满时快速失败；
- Spring 关闭等待：允许已提交任务完成，最长等待 30 秒。

这些值通过配置文件暴露，但没有基准测试支持其为最优值。不能根据这些数字推导
吞吐量、最大并发能力或生产容量。

### 必须保持的生命周期约束

1. `FutureTask` 仍在提交前绑定到当前 `AgentRunContext`；
2. 已接受任务仍由工作线程执行最终 cleanup 和 termination；
3. 被拒绝任务没有工作线程，因此由提交线程进入 `FAILED` 并完成一次清理；
4. 不使用会让 HTTP 线程代跑的 `CallerRunsPolicy`，也不使用静默丢任务策略；
5. 工厂每次返回新 `YuManus`，执行器则由 Spring 单例管理。

### 测试与证据计划

1. 在生产配置不存在时，以轻量 Spring 上下文形成“缺少 `agentRunExecutor`”RED；
2. 以真实组件扫描形成“容器错误持有 `YuManus` 单例”RED；
3. 配置和工厂落地后验证每次创建不同 Agent；
4. 使用 core=1、max=1、queue=1 的真实测试线程池构造“1 运行、1 排队、1 拒绝”；
5. 验证拒绝运行进入 `FAILED`、cleanup 一次、cleanup 时 termination 尚未完成，
   cleanup 返回后 termination 才完成；
6. 回归 10A 以前的 13 项测试，并保存全部原始输出到 `target/evidence`。

本阶段不能证明高并发、性能提升、30 秒内所有外部调用都能停止，也不能证明应用
关闭时不存在残留任务；这些结论留给 10C 的重复运行和关闭验证。

## 16. 阶段 10C 实施预览

### 本阶段解决的问题

有界执行器解决了资源入口无边界的问题，但还需要证明一次停止不会仅让
`FutureTask` 变成 cancelled，而是能够让协作式工作线程退出、执行一次 cleanup，
最后才完成 termination；所有样本结束后执行器也不能留下活动或排队任务。

### 测试结构和指标边界

新增 `BaseAgentExecutorTerminationTest`，使用真实 `ThreadPoolTaskExecutor` 完成
20 轮顺序运行。每轮只有 1 个并发任务，步骤在锁存器上阻塞并响应线程中断，测试
记录“发出停止请求到 termination 完成”的 p95 和最大值，并检查：

- 工作线程确实观察到中断并退出 step；
- cleanup 恰好执行一次，且开始时 step 已经退出；
- cleanup 执行期间 termination 尚未完成；
- 每轮结束后 active=0、queue=0；
- 全部任务结束后线程池可以正常终止。

本阶段的 20 是重复轮次，不是 20 个并发任务。时间样本来自本机、内存锁存器和
可响应中断的测试步骤，只用于建立回归基线，不能描述为接口延迟、吞吐量提升或
生产 SLA。如果模型 SDK、网络 I/O 或工具调用忽略中断，真实终止仍可能超过该值。

### Spring 关闭语义的边界

当前设置 `waitForTasksToCompleteOnShutdown=true`，关闭时会等待已提交任务完成；
`awaitTerminationSeconds=30` 表示最多等待并记录超时，不是 30 秒后强制停止业务
线程。因此本阶段只能证明“所有协作式任务先结束后，执行器无残留并可关闭”，
不能证明应用关闭能强制终止不响应中断的外部调用。

## 17. 阶段 10D 实施预览

### 本阶段解决的问题

SSE 的 timeout、error、completion 和 send failure 来自不同线程和不同阶段。
回调只能请求停止，不能直接 cleanup 或宣告 termination；否则后台任务尚未退出时
下一次运行就可能开始。还需要区分客户端取消与传输失败的最终状态语义。

### 计划文件与关键差异

| 文件 | 动作 |
| --- | --- |
| `BaseAgent.java` | 提取可覆盖的 emitter 创建入口；统一 SEND_FAILURE 到 FAILED 的映射 |
| `BaseAgentSseLifecycleTest.java` | 使用可控 emitter 和真实工作线程触发四类 SSE 事件 |
| 证据账本 | 记录 RED 原因、各场景结果和不能外推的边界 |

### 必须保持的生命周期约束

1. timeout 和 completion 只请求停止，最终状态由工作线程设为 `CANCELLED`；
2. error 和 send failure 使用 `SEND_FAILURE`，最终状态为 `FAILED`；
3. 第一个停止原因不可被随后到达的回调覆盖；
4. 所有事件下 cleanup 仍恰好一次，termination 仍晚于工作线程退出和 cleanup；
5. 测试不得依赖真实网络时序或固定 sleep，而由锁存器建立确定的先后关系。

这组单元测试可以证明 BaseAgent 注册的回调与运行上下文之间的映射，但不能证明
Servlet 容器、反向代理或浏览器在真实网络断开时必然以某个固定顺序触发回调。

## 18. 阶段 10E 实施预览

### 本阶段解决的问题

`BaseAgent` 上的 Lombok `@Data` 会把名称、提示词、最大步骤数和 ChatClient 的
setter 暴露为公共 API。即使运行态已经迁入 `AgentRunContext`，外部线程仍可在运行
中途修改 Agent 配置，造成同一次运行前后看到不同配置。阶段 10E 收紧这条封装边界，
并完成迁移范围、测试稳定性和证据链的最终核验。

### 计划文件与关键差异

| 文件 | 动作 |
| --- | --- |
| `BaseAgent.java` | 删除 `@Data`；仅向子类提供受保护的配置访问方法 |
| `BaseAgentEncapsulationTest.java` | 验证 BaseAgent 不再暴露公共 setter |
| 决策文档与证据账本 | 记录 10B—10E 的问题、方案、代价、故障边界和验证结果 |

### 必须保持的约束

1. 子类构造期间仍能设置 Agent 定义所需配置；
2. 外部调用方不能绕过生命周期边界直接改写配置；
3. `state`、`currentStep`、`messageList` 和步骤 decision 仍只属于 context/局部变量；
4. 生产 Agent 不再回退到公共线程池，`YuManus` 只通过工厂按请求创建；
5. 最终回归必须包含已有隔离、异常、取消、拒绝、终止和 SSE 场景。

删除公共 setter 能降低误用面，但不能让 `ChatClient`、工具回调或其他共享依赖自动
具备线程安全性，也不能阻止子类自身在运行期间错误修改受保护配置。若未来需要在
同一 Agent 实例上并发运行，应进一步把配置聚合成构造后不可变的值对象。

## 19. 阶段 10B—10E 实际结果

### 10B：执行器与 Agent 所有权

- 新增 Spring 管理的 `agentRunExecutor`：core=2、max=4、queue=16、
  `AbortPolicy`，参数均可由配置覆盖；
- 移除生产构造链到 `ForkJoinPool.commonPool()` 的回退入口；
- 移除 `YuManus @Component`，由 `YuManusFactory` 每次创建新实例，控制器只依赖工厂；
- 真实线程池以“1 个运行、1 个排队、1 个拒绝”验证拒绝运行进入 `FAILED`，
  cleanup 一次，termination 晚于 cleanup；
- 配置缺失和错误单例所有权分别形成 RED，17 项阶段回归全部通过；拒绝测试在正确
  实现上首次即通过，因此不虚构缺陷 RED，改用故意颠倒 termination 顺序的 mutation
  证明测试能捕获时序破坏，随后立即恢复。

### 10C：终止延迟与任务残留

在真实专用测试执行器上完成 20 轮顺序取消：并发任务数始终为 1，cleanup 均为一次，
每轮 termination 后 active=0、queue=0。另一个用例在关闭开始前放入 1 个运行中
任务和 1 个排队任务，证明优雅关闭会等待两个已接受任务完成后返回。首次正式样本的
p95 为 0.213 ms、最大值为 6.098 ms。该数字只描述本机、内存锁存器、可响应中断
步骤的测试，不是生产接口延迟或性能提升。

### 10D：SSE 生命周期

5 个行为测试覆盖 timeout、completion/断连、emitter error、send failure 和重复回调。
RED 显示 emitter error 被错误归类为 `CANCELLED`；修正停止原因映射后，前两类为
`CANCELLED`，传输错误为 `FAILED`，重复回调不覆盖第一个停止原因。所有路径均验证
工作步骤退出、cleanup 一次且 termination 不早于 cleanup。

### 10E：封装与最终回归

封装 RED 真实观察到 Lombok 生成 5 个公共 setter；移除 `@Data` 并改为 protected
配置访问后，公共 setter 数量为 0。最终 12 个相关测试类共 25 项测试全部通过。
关键并发生命周期子集又重复 5 轮，每轮 8 项测试，5/5 轮成功；其中每轮包含 20 个
顺序取消样本，最终稳定性核验合计 100 个样本。5 轮 p95 分别为 0.198、0.255、
0.210、0.283、0.199 ms，每轮 residualActive/residualQueued 均为 0。

### 证据结论与边界

这些结果证明当前单 JVM 测试模型中，运行状态隔离、任务提交前绑定、专用资源边界、
拒绝收尾、协作式取消、SSE 状态映射和封装契约能够共同成立。它们不能证明高并发、
吞吐量提升、真实网络回调顺序、外部 SDK 必然响应中断、跨 JVM 取消或生产故障率
下降。原始输出和逐项口径见证据账本记录 04—07。
