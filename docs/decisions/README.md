# 工程决策索引

本目录用于记录项目中需要作出取舍的功能修改和缺陷修复。它不是开发流水账，也不重复基础命令，而是保留“为什么这样改、凭什么相信有效、代价和边界是什么”的可追问证据。

## 使用原则

1. 一个独立技术决策对应一份文档；同一决策的后续修正更新原文，不重复创建近似教程。
2. 架构、并发、生命周期和外部接口变更使用完整模板；纯重命名、格式调整等低风险改动只写简版记录。
3. 设计阶段先记录假设和验证计划，实施后再用真实测试结果替换“待验证”状态。
4. 文档中的测试数量、并发任务数、重复轮次、成功率和性能指标必须分别记录，禁止互相代替。
5. 没有同环境基准测试，不写性能提升；没有压力测试，不写高并发；没有线上数据，不写生产收益。

## 每项重要改动必须回答的问题

| 维度 | 必须回答的问题 |
| --- | --- |
| 问题 | 项目出现了什么可观察问题？ |
| 触发 | 哪些业务场景、线程时序或技术条件会触发？ |
| 根因 | 状态、所有权或控制流为何导致该问题？ |
| 方案 | 使用什么技术解决，关键结构是什么？ |
| 理由 | 为什么需要这样做？备选方案为什么不适用？ |
| 收益 | 具体解决了什么可验证问题？ |
| 代价 | 新增了哪些复杂度、资源成本或行为变化？ |
| 失效 | 方案会如何变坏？规模放大后如何退化？ |
| 边界 | 明确解决不了什么？ |
| 验证 | 用哪些真实行为测试和原始输出证明有效？ |

## 文档状态

- `待审阅`：只有设计和验证计划，尚未授权实施。
- `实施中`：正在形成 RED → GREEN 证据，不代表已经解决。
- `已验证`：聚焦测试和阶段回归通过，证据账本已更新。
- `已废弃`：方案未采用，并在文档中保留原因和替代决策链接。

## 完整记录模板

后续重要改动沿用以下顺序，避免只写“做了什么”而遗漏关键因果链：

1. 背景与可观察问题
2. 触发场景与最小时序
3. 根因与必须保持的不变量
4. 候选方案和取舍
5. 最终设计及职责边界
6. 实施范围和非目标
7. 收益、代价与兼容性影响
8. 故障模式、规模化退化与能力边界
9. RED → GREEN 验证设计
10. 实际证据、结论强度与简历措辞边界

小改动可以合并为“问题、决策、风险、验证”四段，但不得省略验证依据。
